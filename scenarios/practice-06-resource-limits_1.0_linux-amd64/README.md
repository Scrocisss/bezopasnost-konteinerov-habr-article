# Практика 6. Отсутствие лимитов ресурсов

Уязвимость реализована конфигурацией `unlimited` в `compose.yaml`. У сервиса отсутствуют `mem_limit`, `cpus` и `pids_limit`, поэтому cgroups не задают контейнеру собственные потолки этих ресурсов. `limited` использует тот же образ и приложение, но получает лимиты 64 MiB, 0.25 CPU и 32 процесса для сравнения.

`/app/app.py` показывает `memory.max/current`, `cpu.max` и `pids.max/current`. `/app/load.py` — контролируемый нагрузочный помощник с ограничением аргументов и времени; он не является уязвимостью и не запускает нагрузку автоматически.

Проверяйте нагрузочные режимы на сервисе `unlimited`: память — 128 MiB на 5 секунд, CPU — 5 секунд, PID — 48 процессов на 5 секунд. Не запускайте тест памяти на `limited`: его лимит 64 MiB может завершить процесс по OOM. В `limited` подтверждайте ограничения через `/api/status`, `docker inspect` и файлы cgroups. Если вручную повторить PID-тест из 48 процессов в `limited`, создание процессов остановится на `pids.max` и Python может сообщить `BlockingIOError: [Errno 11]`; это ожидаемое ограничение, а не повреждение образа. Дождитесь завершения уже запущенных дочерних процессов перед повтором.

Healthcheck сервиса `limited` имеет увеличенный таймаут, потому что его CPU квота намеренно ограничена до 0.25 CPU. Цель практики — связать системные события, OOM и создание процессов с контейнером и явно учитывать границы Falco: сам факт отсутствия cgroup-лимита может быть виден только через cgroup или Docker telemetry.
